# Polar H10 connection selection repair

> Execute inline using systematic debugging and test-driven development.

**Goal:** Only Polar H10 may connect; retain the user's H10 across launches and recover from an incorrectly saved watch.
**Architecture:** Share model validation and saved-device selection across scanning, OS-connected retrieval, reconnect and restoration. Prefer current advertisement names over iOS cached names; retain verified identity for temporarily unnamed peripherals. Keep the existing unfiltered radio scan so H10 advertisements without service UUIDs remain visible.
**Spec:** User request of 2026-11-15; reject WHOOP and every other model, inspect Alexey Molchanov's available history.
**Tech stack:** Swift, CoreBluetooth, XCTest, UserDefaults.

## Review focus

- Watches returned before H10 by OS retrieval must not stop discovery.
- Legacy watch UUIDs must not survive into automatic reconnect.
- Several H10 straps must not replace the user's saved strap arbitrarily.
- A fresh advertisement must take priority over stale cached names; unnamed legacy devices are unverified.
- Callbacks from canceled/rejected peripherals must not replace the active strap or trigger reconnect.

## Investigation evidence

The production profile was located by first/last name, using read-only PostgreSQL transactions. The existing `usage_events` table contains interval type, time and duration, but no BLE name or peripheral UUID. For the reported participant it contains 54 `ecg_recording` intervals since November 7. On November 15 the recent history includes repeated 5–20 second intervals around 18:12–18:24 UTC. Scalar metric uploads resume at 18:25:17 UTC, including HRV and breathing values. These intervals are derived from `.connected` state, not proof that ECG packets arrived; they cannot identify the watch versus the strap. No production data was changed.

The root cause is independently visible in code: `startScanning` adopted `retrieveConnectedPeripherals(...).first` without identifying the model, `didDiscover` admitted any HR service, and `didConnect` saved every successful UUID under `wythin.polar.uuid`. This could select a watch, stop discovery and persist that choice across launches. Restoration had the same first-peripheral problem.

## Follow-up: show nearby straps while connecting

The user clarified that all nearby Polar straps should remain visible and automatic selection must use the most recently connected one. The existing H10-only connection requirement remains in force.

- Separate the bounded discovery session from connection state; continue accepting advertisements while connecting/connected.
- Opening the Bluetooth picker refreshes all nearby H10s without canceling the current link; keep the list visible below the connected card.
- Scan stops on timeout, closing the picker, or backgrounding; results remain visible. Scan status has its own observable flag.
- Auto-select only the saved H10, even if a different H10 is the sole OS-connected device. With no saved strap, wait for a tap.
- Do not switch back to the old saved H10 while a manually chosen new strap is connecting. Persist the new UUID only on a successful connection.
- Manual device changes clear the signal buffer across the connection gap.

Regression coverage: list retains all three H10s across connecting/connected states; manual selection cannot be interrupted by the old strap's advertisement; WHOOP and late advertisements are excluded; a lone unpaired H10 is not auto-selected; most recently connected H10 survives relaunch as the only automatic target.

Follow-up review found that a queued picker scan could suppress the saved H10's persistent connection request. `ensureAutoConnect` now uses the same connection-state eligibility policy as discovery and allows a cached saved strap to be armed while scanning; radio scanning is only checked to avoid redundant fallback scans. The test for an orphaned `.connecting` state after connection failure was observed failing, then fixed by resetting to `.scanning` when no peripheral remains.

Deferred minor from review: requesting a scan when Bluetooth is already off/denied/unsupported can show a waiting scan indicator until another central-state event or explicit Stop. The original Scan action already had this behavior; opening the picker now also requests scanning. It does not permit connections to an unsupported device. Previously noted raw-archive, write-error and standby behaviors remain outside this change.

Follow-up final verification: all 1,702 iOS tests passed, including 83 BLE tests; `xcodebuild test` exited 0 and `git diff --check` passed. No hardware run or TestFlight upload was performed.
